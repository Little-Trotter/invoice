= Architecture Decisions

This chapter curates the architecturally significant decisions behind the current system. They
are drawn from two sources: the project's running decision logs (architecture decision records and
architecture analyses, referenced below by topic) and decisions documented only in code and project
practice, which are recorded here for the first time as a proper ADR. Curation favors
significance over completeness: this is not every decision ever made, only the ones that shape
the architecture a maintainer needs to understand today. The originating documents are
left untouched; each ADR below cites its source.

ADR-016 and ADR-019 are merged into <<adr-015,ADR-015>>; both numbers stay reserved and both
anchors still resolve, so existing references to either keep working.

A new ADR uses the sections Status, Context, Decision, Alternatives Considered and Consequences.
Its Status names the *PO approval (date)* whenever the decision changes what users or recipients
see in generated output (PDF pages, XML content, mail text); without that entry the change is not
merged.

== ADR-001: Money Value Type Instead of Raw BigDecimal

* *Decision*: All monetary arithmetic is encapsulated by `Money` (`kotlin-shared`), never raw
  `BigDecimal`.
* *Consequence*: Universal `HALF_UP` rounding at scale 2, enforced via ArchUnit gates
  (`MoneyArchitectureTest`) across all modules.

[[_adr_002_en_16931_business_terms_as_a_kotlin_enum]]
== ADR-002: EN 16931 Business Terms as a Kotlin Enum, Not a Seeded Catalog Table

* *Decision*: Full EN 16931 business-term taxonomy is modeled as a Kotlin enum (`B2bTerm`,
  `SMALLINT` BT-code), replacing seeded database catalog tables.
* *Consequence*: Compile-time validation and refactoring safety for all e-invoicing terms instead of
  late runtime database errors.

include::decisions/002-b2b-term-enum.adoc[leveloffset=+2]

[[_adr_003_reverse_charge_at_invoice_level]]
== ADR-003: Reverse Charge Is an Invoice-Level Decision, Not Derived from Line Items

* *Decision*: `Invoice.reverseCharge` is declared at the invoice header, cascading tax rules
  downward to all invoice items.
* *Consequence*: Mixed tax treatments on a single invoice are eliminated by construction;
  disagreements trigger a blocking finalization gate.

include::decisions/003-reverse-charge-invoice-level.adoc[leveloffset=+2]

* *Decision*: Superseded; PDF layout is a single product-shipped Typst template, with no per-profile
  assignment or print-time template choice.
* *Consequence*: Layout changes are made in code, not through master data.

[[_adr_005_german_system_time_everywhere]]
== ADR-005: Displayed System Time Is Always German Local Time

* *Decision*: All display timestamps use `Europe/Berlin` as default via a centralized `GermanTime` constant, while technical persistence and messaging remain in UTC.
* *Consequence*: Deterministic date/time rendering across all time zones and container environments, with capability for multi-timezone branch offices in mid-sized enterprises.

include::decisions/005-german-system-time.adoc[leveloffset=+2]

[[_adr_006_jpa_access_pattern_hardening]]
== ADR-006: JPA Access Pattern Hardening (LIKE Escaping, Stable Pagination, Explicit Fetches)

* *Decision*: Mandatory wildcard escaping for `LIKE` queries, deterministic tiebreakers in paginated
  queries, and explicit entity fetch joins.
* *Consequence*: Elimination of query injection vectors, unstable page shifts, and Hibernate lazy
  initialization surprises.

include::decisions/006-jpa-access-hardening.adoc[leveloffset=+2]

[[_adr_007_rustfs_object_storage]]
== ADR-007: RustFS as the S3-Compatible Object Store, Including on Small-Budget Hardware

* *Decision*: RustFS (S3-compatible) serves as the standard object store for receipts and generated
  documents across all hardware profiles.
* *Consequence*: Unified S3 API from local dev to mini-PC and cloud, replacing fragmented local
  filesystem storage.

include::decisions/007-rustfs-object-storage.adoc[leveloffset=+2]

[[_adr_008_nats_envelope_principle]]
== ADR-008: Small NATS Envelopes, Valkey for Text, RustFS for Binaries

* *Decision*: NATS carries only lightweight reference envelopes. Binary documents live in RustFS;
  cached text payloads live in Valkey.
* *Consequence*: Constant message size and low queue memory footprint independent of invoice
  document payload sizes.

include::decisions/008-nats-envelope-principle.adoc[leveloffset=+2]

* *Consequence*: Eliminates domain state mutation bypassing aggregate rules and prevents entity

* *Amended by*: <<adr-027,ADR-027>> — the command entry points are the `*UseCase` input ports.

* *Decision*: The sellable catalog is partitioned into three explicit categories (Material, Unit

* *Consequence*: Prevents illegal unit combinations in e-invoice XML before positions reach the
  invoice drafting stage.

[[_adr_027_dedicated_input_ports_per_use_case]]
== ADR-027: Dedicated Input Ports per Use Case, No Composite Interfaces

* *Decision*: UI and inbound adapters inject narrow role interfaces in
  `application.<context>.port.inbound` — `*QueryPort` for reads, `*UseCase` (a `CommandEntryPoint`)
  for writes; composite interfaces and `*Facade` types do not exist.
* *Consequence*: Each caller depends only on the use cases it calls; ArchUnit
  (`InputPortArchitectureTest`) enforces naming, the 12-method cap and the no-composite rule.

include::decisions/027-role-interfaces-over-composite.adoc[leveloffset=+2]

== ADR-028: Optimistic Concurrency, First Committed Writer Wins

* *Decision*: Every aggregate write checks the caller's `expectedVersion` against the aggregate
  root's `@Version` before mutating; invoice items and trips check `Invoice.version`, not their
  own entity-level version column. A mismatch rejects before any row is touched.
* *Consequence*: No lost updates across header, items, trips, recipient, article and reference
  data; one conflict notion and one optimistic-lock notification UI-wide. See
  <<_concurrent_editing,Concurrent Editing>> (Chapter 8) for the per-entity coverage table.

include::decisions/028-optimistic-concurrency-first-writer-wins.adoc[leveloffset=+2]

== ADR-029: A Single Injectable Time Source, Two Readings of One Moment

* *Decision*: `TimeSource` replaces direct `now()` calls; points in time (`instant()`, `nowUtc()`)
  are UTC, calendar dates (`today()`, `localNow()`) are read in `Europe/Berlin`. Database, event streams,
  and RustFS store timestamps strictly in UTC, while UI presents local time (default `Europe/Berlin`).
  Invoice numbers are drawn for the invoice's own business date, not the allocation instant.
* *Consequence*: Year/month-boundary behavior is deterministically testable by fixing one clock;
  business logic no longer depends on the container's `TZ`. The database never reads its own
  clock: no time defaults, the audit trigger stamps from `app.now`. Multi-timezone operations for
  branch offices are inherently enabled. Enforced by ArchUnit in every module.

include::decisions/029-single-time-source.adoc[leveloffset=+2]

== ADR-030: Typst as the Only Layout Engine

* *Decision*: The base PDF is rendered by the Typst CLI, a pinned, checksum-verified binary
  running as a sandboxed subprocess of `kotlin-xpdf` (`TypstCompiler`), never as a separate
  service. Typst is the product's only layout engine: there is no engine switch, no second
  engine and no uploadable template format. Templates are layout only and receive preformatted
  data; output is byte-deterministic.
* *Consequence*: The pipeline after the base document (Mustang, post-render mark, veraPDF) runs
  on the Typst base document. Exactly one standard Typst template ships in the worker image;
  layouts change in code only, and there is no template catalogue or administration tab. The
  Typst fixtures are the only layout reference; an ArchUnit rule keeps `net.sf.jasperreports..`
  out of `kotlin-xpdf`. Verified by `TypstCompileIT` against the containerised pinned CLI.

include::decisions/030-typst-layout-engine.adoc[leveloffset=+2]

== ADR-031: EXTENDED Profile Escalation for Cash-Discount Invoices

* *Decision*: EN16931 remains the default B2B profile. An invoice carrying a cash discount on the
  Mustang route is escalated to EXTENDED (opt-in via the admin feature flag
  `feature.extended-profile.enabled`, off by default) so the discount travels as structured
  `ApplicableTradePaymentDiscountTerms` in addition to the BR-DE-18 `#SKONTO#` text line. The
  profile is resolved once in `kotlin-invoice` (`resolveExportProfileId`,
  `Invoice.requiresExtendedProfile`) and consumed by both the finalization gate and the XML export.
  XRechnung is never escalated.
* *Consequence*: Receivers without EXTENDED support may reject the profile, although the document
  remains EN 16931 conformant. EXTENDED is an EN-16931-conformant extension, so escalation occurs
  only where the data justifies the extra profile layer. XML-level validation confirms CII-XSD and
  Factur-X EXTENDED Schematron conformance; the KoSIT stage is skipped for EXTENDED exports with a
  dedicated `PROFILE` stage carrying a WARNING finding; overall validation stays VALID. The
  `validation_profile` registry holds an EXTENDED row in state EXPERIMENTAL (Factur-X 1.09.2
  Schematron, Mustang 2.26.0).

== ADR-032: One Receipt, One Embedding

* *Status*: Superseded by <<adr-039,ADR-039>>; the decision below is kept as history.
* *Decision*: A receipt is embedded exactly once in a produced e-invoice — as the BG-24
  `AdditionalReferencedDocument`/`AttachmentBinaryObject` (Base64) inside the ZUGFeRD XML
  (`MustangTransactionBuilder`). The rasterized annex pages and the separate PDF/A-3 embedded file
  are both removed; `ReceiptAnnexBuilder` is deleted. Receipts are reduced at upload
  (`ReceiptUploadService` → `ReceiptPdfReducer` → `PdfBoxReceiptPdfReducer`, PDFBox) towards
  `ReceiptSizePolicy.TARGET_RECEIPT_SIZE` (440 KiB) instead of only being rejected when oversized;
  the pool stores only the reduced derivative, never the original upload.
* *Consequence*: A 19-receipt invoice's container size is bounded by one copy of each receipt
  instead of the former three, keeping it well inside mail-gateway and archive-volume limits.
  `CombinedDocumentSizeEstimator` (`kotlin-shared`) sizes the budget on the Base64-encoded receipt
  bytes plus a fixed reserve. Upload-time rasterisation (stage 2) loses a receipt's text layer; a
  user may still decline reduction up to `MAX_UNREDUCED_RECEIPT_SIZE` (1 MiB), and the export
  worker's backstop (`PdfExportServiceImpl.enforceSizeBackstop`) still refuses an oversized
  container rather than truncating one.

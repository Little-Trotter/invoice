= Deployment View

The target environment is called the **server** throughout this document. The primary target is
an Ubuntu server; a dedicated single-instance host (a mini PC or any other standalone machine
serving one operator) is the second supported shape, covered in
<<_dedicated_single_instance_host_mini_pc,Dedicated Single-Instance Host>> below. This
repository's own `docker-compose.yml` is the minimal product stack — the application, the
renderer/worker, and the four infrastructure services it needs (PostgreSQL, RustFS, NATS,
Valkey), no TLS proxy, no monitoring, no hardening overlays. The full production-style deployment
described in this chapter — native Postgres/RustFS/Caddy, the instance overlay, backups, and
monitoring — is assembled by the sibling, private `little-trotter-admin-tools` repository, which
layers its own Compose overlays and native-install scripts on top of this repository's base file
rather than duplicating it. Every path below prefixed `docker/compose/` or `admin-tools/`
therefore refers to that sibling repository, checked out alongside this one.

Productive use is a server installation by an IT service provider, following the Ubuntu server
deployment described below. This repository's `make dev` compose stack is meant for evaluation
and development only.

== Server Deployment (Production-Style Target)

.Server deployment
image::c4-server-deployment.svg[C4 deployment diagram of the Ubuntu server: native shared services and one Docker Compose project per instance]

On the Ubuntu server, PostgreSQL 18, RustFS, and Caddy run *natively* under systemd — one
installation of each, shared by every instance on the box — instead of as Docker containers.
Only the application layer (`little-trotter-invoice`, `little-trotter-job-worker`, `kotlin-xpdf`,
NATS JetStream, Valkey) is Docker Compose, running as *one compose project per instance*
(`little-trotter-prod`/`little-trotter-dev`/`little-trotter-demo`), each with its own Docker
subnet and its own database, bucket, and role-trio on the shared native services. Caddy is the
stack's only externally exposed edge: one shared installation generates one HTTPS vhost per
instance (ports `443`/`80`), reverse-proxying to that instance's own `little-trotter-invoice`
container on a loopback-only port — every other container, native or Docker, stays unreachable
from outside the server. Authentik and the monitoring stack (Prometheus/Grafana) are shared
Docker services outside every instance project: Authentik is the identity provider for the
Office Manager login of every instance (`little-trotter-invoice` runs as a Quarkus OIDC web-app client
against it, the application itself decides who may do what) and additionally gates the separate admin site; monitoring
scrapes every instance's metrics endpoint.

Instance ports follow one offset scheme (`prod` +0, `dev` +10000, `demo` +20000) — for example
the application's loopback port is `8080`/`18080`/`28080` and NATS' client port is
`4222`/`14222`/`24222` — while the two shared native services keep one fixed port each,
independent of instance count: PostgreSQL `5432` and RustFS `9010`.

`kotlin-xpdf`'s image renders with the pinned Typst CLI only (<<adr-030,ADR-030>>); there is no
second layout engine, no engine switch and no optional build profile for one.

PostgreSQL and RustFS keep their data directly on the server's own filesystem, outside Docker's
storage driver (systemd-managed data directories, not named volumes) — one reason they are native:
independent backup, resize, and migration. The Docker-side volumes that remain are per instance and
named per compose project, so three instances never collide. `little-trotter-invoice`'s own
`backups-data:/backups` volume is where DevOps's cron-triggered backup run (see
<<_operations_and_admin_tooling_little_trotter_admin_tools,Operations and Admin Tooling>> below)
writes its archives before `backup.sh` copies them off, syncing an age-encrypted copy to an optional
external SSD for `prod`.

Backups serve recovery, not archiving; retention is covered by the operator's archive
(<<adr-035,ADR-035>>). Disk encryption at rest (for example LUKS) of the host is the operator's
responsibility; the age encryption above applies to backup copies only.

Reaching the server: `sudo lt-setup build prod|dev|demo` resolves that instance's ports,
installs/adopts native Postgres, RustFS, and Caddy, adopts monitoring and Authentik if present,
and deploys the instance's Docker Compose project (`QUARKUS_PROFILE=prod`, scheduler enabled on
both Quarkus services).

=== Dedicated Single-Instance Host (Mini PC)

The second deployment shape is one machine for one deployment: a mini PC that serves a single
operator. It runs this repository's `docker-compose.yml` as it is — no instance model, no
shared native services — so every service is a container, PostgreSQL, RustFS and Caddy included.
Caddy sits on `proxy-net` and is the only service with published ports; everything else lives on
`invoice-net`, reachable from the host on `127.0.0.1` at most.

[cols="2,2,1", options="header"]
|===
|Service |Reachable at |Memory limit

|`caddy` |`80`, `443` (the only ports open beyond localhost) |128M
|`little-trotter-invoice` |via Caddy only |1200M
|`little-trotter-job-worker` |not reachable (no UI) |432M
|`kotlin-xpdf` |internal only |768M
|`postgres` |`127.0.0.1:5432` |768M
|`rustfs` |`127.0.0.1:9000` (S3), `127.0.0.1:9001` (console) |400M
|`nats` |`127.0.0.1:4222`, `127.0.0.1:8222` |128M
|`valkey` |not published |192M
|===

Every container carries a memory limit (about 3.9 GB in total) and the application tier a `pids`
limit; a tighter overlay for smaller machines brings the total down to about 2.6 GB. Database and
object-store data live on bind mounts under `/srv/little-trotter`, so they survive a full
container and image cleanup. The stack is deployed with `make -C admin-tools deploy`, which picks
the hardware overlay automatically and can pull published images instead of building them.

The memory limit above is a hard ceiling: `little-trotter-invoice` and `little-trotter-job-worker`
both run with `-XX:+ExitOnOutOfMemoryError`, so a burst of concurrent PDF/XLS/report generation work
that exceeds it kills the whole process rather than degrading. The
`invoice.generation.bulkhead.max-concurrent-calls` knob
(`INVOICE_GENERATION_BULKHEAD_MAX_CONCURRENT_CALLS` / `_WORKER`, see `docker-compose.yml`) exists to
keep worst-case concurrent generation work under whichever memory limit a given overlay configures;
a rejected call fails cleanly into the existing durable `PENDING` job record
(<<_generate_e_invoice,Generate E-Invoice>>) rather than dropping work or risking the OOM kill.
Interactive document jobs pass a separate bulkhead,
`invoice.generation.interactive-bulkhead.max-concurrent-calls`
(`INVOICE_GENERATION_INTERACTIVE_BULKHEAD_MAX_CONCURRENT_CALLS`, default 4), so a full bulk bulkhead
never rejects them; its memory share counts on top of the bulk limit. On the `kotlin-xpdf` side,
`JOB_INTERACTIVE_WORKER_THREADS` (default 1) adds the interactive render threads, which the derived
bulk thread count already subtracts from the heap budget.
`docker-compose.yml`'s own comment on that variable carries the sizing arithmetic for this
repository's default limits; a hardware overlay that lowers the memory limit further (as this
section's mini-PC table does) must lower this knob to match, which is out of this repository's scope
to prescribe for a sibling repository's overlay.

== Optional Mail Dispatch Container

The mail dispatch component (`kotlin-email`, see
<<_building_block_view,Building Block View>>) sends invoices by email. It is a separately built
and deployed container so this bounded context — templates, provider SMTP, an append-only send
journal, signed archive packages — has its own release cycle and failure domain, and so an
instance can run with or without it: mail dispatch is never on the invoicing application's
critical path.

It plugs into the stack the same way the optional Factur-X engine overlay (standby, kept but not
developed further) does — an `email` Compose profile in admin-tools, switched on per instance by one
flag (`LT_MAIL_ENABLED`; in development `make dev` starts it by default, `EMAIL=0` opts out) — with
no port published to the internet; Caddy answers 404 for `/mail/*` from outside, and only the invoicing application calls the
component's REST API. Composing a mail is one HTTPS request into the
component, attachments handed over as presigned links rather than a shared bucket; the outcome comes
back asynchronously on the NATS subject `mail.send.result`, projected onto two nullable columns on
the invoice so the send history stays visible even with the component stopped. The design decisions
(own bounded context, published contract package, forwarded identity headers) are recorded in
<<adr-015,ADR-015>>, <<adr-016,ADR-016>> and <<adr-019,ADR-019>>; this section covers only how the
component is deployed. An instance that leaves the flag off carries none of it — no container, no
schema, no bucket, no streams, no secret. Every test stack (isolated Playwright stack, stress,
admin-test, dev) and the cross-module E2E suite run the real component with a Mailpit sink, never a
stub; a stub HTTP server remains only in integration tests that deliberately isolate the invoicing
side's HTTP adapter (retry/timeout, malformed answers).

[cols="2,3", options="header"]
|===
|Switch |Effect

|`LT_MAIL_ENABLED` (instance), `EMAIL` (dev, on by default)
|Starts `email-app` plus its schema, bucket and NATS streams; the invoicing image itself is
unchanged either way.

|Port
|`LT_MAIL_PORT` (8090 / 18090 / 28090), `127.0.0.1` only — called by the invoicing application
over the instance network; no port reaches the network.

|Provisioning
|Switching the flag on provisions everything the component needs on the host automatically: the
`mail` database schema with the `mail_app`/`mail_migrator` roles, the `mail-journal` object-store
bucket with its access key, the archive-signing key pair and the integration bearer token; the component creates its own JetStream streams at start. The
only human input is the instance name; no value is typed or pasted.

|Transport (`MAIL_TRANSPORT`)
|`sink` (dev/demo only) points SMTP at a loopback Mailpit sink so no mail leaves the host;
`provider` (prod) uses the SMTP provider credentials from the server-local sealed file
`/etc/little-trotter/mail-provider.properties.age`, decrypted only in the deploy process's
environment at start time — the plaintext never exists as a file, in the instance env, in a log or
in a repository. A prod instance without a sealed provider file refuses to enable mail (exit 2,
env untouched).

|Archive
|The mail secrets of an instance (mail env keys, archive-signing key pair, and the still-sealed
provider file with its key) can be exported as one age-encrypted archive under the instance backup
directory and restored into a fresh env without overwriting existing keys; the archive never
contains a plaintext provider password.
|===

[NOTE]
====
The integration is opt-in. New instances keep `LT_MAIL_ENABLED=false`; enabling it on a production
instance requires the sealed provider file to exist on the host first, so mail is switched on in
one step once the SMTP provider and its audit requirements are settled.
====

== Optional Quote Container

The offer module (`kotlin-quote`, see <<_building_block_view,Building Block View>>) is deployed
like the mail component: a separate `quote-app` container behind the Compose profile `quote`
(overlay `docker/compose/quote.yml` in admin-tools, switched on per instance by
`LT_QUOTE_ENABLED`; `make dev QUOTE=1` in development), reached by the invoicing application
over the instance network. It reuses the instance's PostgreSQL and RustFS but is isolated by name:
schema `quote` in the existing database with its own role pair (`quote_migrator`, `quote_app`), own
bucket `quote-documents`, own NATS streams. No port is published; Caddy answers 404 for
`/quote/api/*` and `/quote/q/*` from outside. The invoicing application gates menu, publisher and
consumer with `quote.enabled` (`QUOTE_ENABLED`, off by default); an instance that leaves it off
carries no container, schema, bucket or stream of the module. Offer PDFs are produced by the
existing renderer through the document-job subject; offers are sent through the mail component,
so a quote instance that sends offers also runs the mail component.

== Database Baselines: What Runs When

Two independent Flyway baselines exist, one per component, in the same PostgreSQL database but in
separate schemas with separate history tables. Neither is an upgrade path: while no live instance
exists, both are edited in place (greenfield baseline, no `V3`+ scripts, no backfills).

[cols="2,3", options="header"]
|===
|Baseline |Runs

|Invoice `ddl/V1__baseline_schema.sql` + `seed/V2__baseline_seed.sql` (`kotlin-invoice`)
|At every start of the invoicing application (Flyway, `lt_migrator`). Independent of
`MAIL_ENABLED`; the invoicing application never references the `mail` schema and talks to the
component only over HTTP and NATS.

|Mail `V1__mail_baseline_schema.sql` + `V2__mail_baseline_seed.sql` (`kotlin-email/email-service`)
|Only by `email-app`, and only when the component runs (`MAIL_ENABLED=true` / `LT_MAIL_ENABLED`),
as `mail_migrator` into schema `mail` (history table `flyway_schema_history_mail`). With the flag
off the schema is never created.

|Roles `mail_migrator` / `mail_app` (`db/roles/mail_roles.sql`, not a Flyway migration)
|Once, against the instance's existing database, before the first mail migrate (role bootstrap of
the deployment). The mail baseline then grants and revokes against these existing roles.
|===

Verification: a fresh isolated PostgreSQL starts the invoicing application with the invoice
baseline alone (`FeatureModulesAlwaysActiveIT`); with the flag off no NATS result consumer is bound
and the start-up log carries no mail-related warning.

== Operations and Admin Tooling (`little-trotter-admin-tools`)

Server operations, instance lifecycle management, and disaster recovery are strictly separated from
application code and orchestrated by the sibling repository `little-trotter-admin-tools` (currently
maintained as an internal operator suite by the project initiator; public release planned for Q4/2027 or
Q1/2028 after multi-year operational maturity validation; operators in the interim reduce operational
effort through reference hardware and administrative scripts).

=== Staged Operations Rollout: Lean MVP Baseline vs. Phase-2 Management Plane

The operational lifecycle follows a lean, two-stage rollout model to eliminate operational waste (*Muda*) and ensure compliance-grade robustness:

* *Phase 1 (Operational MVP / Current Baseline until Q4/2027):*
** *Lean Reference Hardware:* Standardized fanless Mini-PC paired with local mirrored NAS, eliminating platform-specific driver, thermal, and configuration anomalies.
** *Lightweight Shell Automation:* Dedicated shell and CLI scripts maintained by the project initiator handle core operational tasks (age-encrypted backups, atomic PostgreSQL snapshots, container rollouts, and systemd watchdog verifications).
** *Operator Baseline:* Achieves an empirically validated run-effort of 2–3 person-days per year (0.75–1.5 person-days initial ramp-up).
* *Phase 2 (Consolidated Management Plane / Release Q4/2027–Q1/2028):*
** *General Availability of little-trotter-admin:* Packaged Go CLI suite (`lt`) and interactive TUI (`lhorse`).
** *Phase-Gate Quality Criteria:* Transition to Phase 2 requires proven completion of an operational hardening cycle under real-world production conditions:
*** Non-disruptive PostgreSQL schema evolution across major version migrations.
*** Validated automated disaster recovery rehearsals with Mean Time to Recovery (MTTR) < 15 minutes.
*** Long-term zero-maintenance operation of certificate renewal, Authentik forward-auth, and storage reclamation under sustained production accounting loads.

=== Manual Database Writes

The database never invents a time (<<adr-029,ADR-029>>): the invoice audit trigger stamps
`occurred_at` from the session setting `app.now` and rejects a write without it. The application
sets `app.now` itself; every operator write outside it — a `psql` session, an ad-hoc script, a
bulk loader — that inserts, updates or deletes rows of `invoice`, `invoice_item`,
`invoice_document`, `trip_expense` or the receipt assignments sets it first, in the same
transaction, in UTC:

[source,sql]
----
BEGIN;
SELECT set_config('app.now', '2026-09-27T08:00:00Z', true);
-- the corrective statements
COMMIT;
----

Without it the write fails with `app.now is not set: a write to <table> must carry the application
time`. Columns that carry the application time (`invoice.invoice_date`, the `created_at`
of snapshots, jobs, validation data and maintenance events, `maintenance_queue_execution.claimed_at`)
have no database-clock default; a manual `INSERT` supplies them explicitly.

Not affected: read-only `psql` access, and `lt backup restore` — a full `pg_restore --clean`
loads the data before it recreates the triggers. The `datagen` loader sets `app.now` on every
connection it opens.

== Verification on the Test Host

At the end of a wave, the result is verified on the test host, not on the developer machine. The
host runs its own Docker Compose stacks and never touches existing instance data.

[arabic]
. Transfer: the commits are sent as a `git bundle` and checked out into a dedicated, detached
  worktree on the host.
. Isolation: every run uses its own Compose project name (for the Playwright stack
  `E2E_PROJECT=<name>`), its own network, and a fresh database. Test data is limited to the
  synthetic `datagen` data.
. Order: Playwright suite, then the dependency scan (see
  <<_dependency_vulnerability_scanning,Dependency Vulnerability Scanning>>), then `make test`.
. Cleanup: `docker compose -p <name> down -v`, then remove the worktree.

Long jobs run in a login shell (`bash -lc '...'`). User-installed linters such as `ruff` live in
`~/.local/bin`, which a non-login SSH shell does not have on `PATH`; without it the config lint
gate fails.

=== Playwright Harness Behavior

* *`ERR_NETWORK_CHANGED`:* Chromium reports this on page loads when Testcontainers creates or
  removes Docker networks on the same host in parallel. The request never reaches the server. The
  harness reloads once and reports the application as offline only if the error persists.
  Integration test suites therefore do not run in parallel with Playwright.
* *Grid cells:* Vaadin renders grid cell content in the light DOM inside
  `vaadin-grid-cell-content`, outside the `[role=row]` element. Status symbols are
  `span[role=img]` elements with an `aria-label`. Locators target the cell content, not row
  descendants.
* *Notifications:* an open error notification is not replaced by a later success notification
  (one toast slot per UI). A test dismisses the error before asserting a following success toast.

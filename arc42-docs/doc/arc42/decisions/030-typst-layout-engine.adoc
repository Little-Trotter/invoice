[[adr-030]]
= ADR-030: Typst as the Only Layout Engine

== Status
Accepted, 2026-09-27

PO approval (visible output): 2026-10-14 neutralized payment hint (`payment.hint.noBankDetails`) and quotation validity clause (`validity.clause`) labels across DE and EN bundles.

== Context
The base PDF of every invoice is a typeset document that Mustang turns into a Factur-X
attachment with XMP and that veraPDF then checks. The layout engine has to express DIN 5008
geometry in millimetres, produce byte-identical output for identical input (golden tests,
archive content hashes), export PDF/A-3b with embedded files natively, and run in the worker
without a heavy reflection-based dependency tree.

Typst is a typesetting compiler with a native PDF/A-2b/3b export, embedded-file support, absolute
millimetre positioning, repeatable table headers, German hyphenation and byte-identical output
for identical input. It is a Rust binary without a JVM binding, pre-1.0 (0.15.x), released under
Apache-2.0. There is no official container image and no visual designer.

== Decision
Typst is the layout engine — the product's only one, not a deployment choice. No other layout
engine, engine switch, fallback or uploadable template format exists: Jasper was retired on
2026-09-29 and there is no Jasper module,
no Maven profile for one, no JRXML catalogue, no `ServiceLoader` extension point for a second
engine and no template-admin upload. An ArchUnit rule pins `net.sf.jasperreports..` absent from
`kotlin-xpdf`'s dependency graph as the guard against reintroduction.

Engine boundary:: The Typst CLI runs as a subprocess of `kotlin-xpdf` (`TypstCompiler`),
exactly the shape veraPDF already has (`VeraPdfCliValidator`): a pinned, checksum-verified
binary installed into the worker image (`kotlin-xpdf/Dockerfile`, `INSTALL_TYPST`, default on),
never a separate service. A service would add a network hop, a second deployable and an
authentication question to a call that takes milliseconds and has exactly one caller. The
pipeline after the base document — Mustang attachment and XMP, color-space normalization,
post-render mark, receipt embedding, veraPDF — runs on the Typst base document.

Sandbox:: Every run gets a fresh, owner-only working directory; `--root` confines file access
to it, `--ignore-system-fonts` plus `--font-path` pin the glyphs to the fonts the project ships
(the Liberation Sans files), and Typst has no network or shell
access. A template is data, never code.

Determinism:: The creation timestamp is passed explicitly from the shared time source
(<<adr-029,ADR-029>>), so identical inputs yield byte-identical PDFs. Golden tests and archive
hashes rely on it.

Layout only:: Templates receive preformatted strings (`data.json`) — amounts, dates,
quantities are formatted by the Kotlin side with its `Money` and locale rules. A template never
calculates or rounds; the figures on paper are the figures the domain computed.

Engine selection:: There is none — Typst renders every invoice through the role interface
`BasePdfRendererPort` (`kotlin-shared`, `InvoiceDto` → PDF bytes), implemented by
`TypstInvoiceRenderer`; no `XPDF_RENDER_ENGINE` variable exists, so a deployment cannot change how
invoices render. `/status/typst` reports Typst's own availability and its installed and pinned
version, mirroring `/status/verapdf`.

Shipped layout only:: The worker image ships exactly one template, `standard-invoice.typ`; the
layout lives in code. Layout changes are made in code or by the operator through admin tooling —
not by users. There are no user-uploaded template rows, no shipped-template manifest, no
compile-verify endpoint and no template fingerprint on `generation_job`.

The payment block also carries an optional GiroCode (EPC QR code), generated by the Typst
renderer and controlled by the `XPDF_PAYMENT_QR` environment variable (`on`/`off`, default `on`,
case-insensitive); a value that is neither fails the service at startup rather than silently
dropping the code from every invoice.

The visual design system — two card styles, color discipline and the five-step type scale —
is implemented in the template and described in the section "Design system" below.

== Target structure
`TypstInvoiceRenderer` (`kotlin-xpdf`) builds `data.json` from `InvoiceReportModel` and compiles
the shipped `standard-invoice.typ` through `TypstCompiler`. `BasePdfStage` and `RenderWarmup`
depend on `BasePdfRendererPort` only. The report model carries structured fields (info-box rows,
identifier sublines, fitted footer lines) and `FreeTextMarkup` a structured rendering, so the
template composes its cells from data and never parses markup.

== Verification
`TypstCompileIT` runs against the containerized pinned CLI and proves PDF/A-3b identification,
output intent, embedded fonts, byte-identical reruns, repeated table header across pages and
diagnostics on a broken template. The full export (receipt embedding, Mustang attachment, brand
mark) is accepted by veraPDF 3b on the Typst base.

== Flow layout, geometry only in Typst

The template comprises two layers. The head is absolutely positioned on the DIN 5008 fixed points
(in points): teal and orange letterhead, sender name at y = 20 pt, return address line at y = 77 pt
with separator at y = 90 pt, address window at y = 100–140 pt, subject at y = 255 pt, fixed head
height 290 pt, footer top at 764 pt. The head's right column — an absolutely anchored stack at x =
265 pt, y = 22 pt, width 216 pt — holds content-sized info cards (invoice data, tax IDs) bounded to
245 pt in height; card content wraps to grow the card, font sizes never shrink.

The flow body below the head contains no absolute positioning: free text, items table, tax
breakdown card, totals card, payment card and notes. Every box is sized by its content. All
geometry lives in design tokens at the template's head (colors, typography scale, 4-point
spacing grid, line pitch, named column widths); Kotlin delivers preformatted strings in
`data.json` and no measures.

Flow rules enforce document structure: tax and totals cards are unbreakable as a unit; payment
and notes stay together on one page by measuring and using `sticky` as fallback; the items
table header repeats across pages, rows never split. Gaps between blocks come only from
spacing tokens. The VAT column is auto-width with a minimum so values like "19,00 %" stay on
one line. Kotlin no longer fits any text for Typst: the sender name, the return address line and
the footer contact lines arrive raw in `data.json` (`sender.name`, `sender.returnLine`,
`footer.contact[].text`). One template function, `fit-line`, measures each of them in
context and picks the first size of a token ladder that fits its column (sender name
16/14/12 pt on one line, then two wrapped lines down to 9 pt; return line and contact
lines 7.5/7/6.5/6 pt); when nothing fits, the smallest size prints with the text
shortened and an ellipsis. The free-text placement rule (inline versus after the table) is a
model decision, not a template one.

== Design system

The template follows Bauhaus principles (form follows function, one signal color, no
ornament) with a Material-style tonal surface instead of card borders: exactly two card
styles exist, a plain tonal area and the same area with a 2 pt accent bar down its left edge
for the one emphasised card (payment). The two brand colors are each pinned to a short,
named list of places so neither drifts onto a third use by accident.

[cols="1,2,2"]
|===
| Token | Value | Used for

| `ink`
| `#2C3E50`
| body text, values

| `muted`
| `#7F8C8D`
| labels, sublines, footer

| `surface`
| `#F4F6F8`
| the one card/zebra fill; filled cards carry no stroke

| `border`
| `#D5D8DC`
| hairlines only — a table's bottom edge, the totals card's rule above the gross row

| `teal`
| `#16A085`
| the header bar and the table head, nowhere else

| `accent`
| `#E67E22`
| header-bar block, gross total, footer line
|===

Typography is a five-step scale; every text size in the template names one of these tokens
(the DIN 5008 address window is the one exception, kept literal since its geometry predates
and is independent of this design pass):

[cols="1,1,3"]
|===
| Token | Size | Used for

| `t-headline`
| 16 pt
| sender name

| `t-title`
| 14 pt
| subject line, the totals card's gross row

| `t-body`
| 9.5 pt
| totals net/VAT rows, payment rows, note text, payment hint

| `t-table`
| 8.5 pt
| items table body, info-card rows, tax rows, item description

| `t-label`
| 7.5 pt
| card/table/note labels, sublines, footer, return line, QR caption
|===

Spacing keeps the existing 4 pt grid (`s1`…`s6`) and two line pitches (12 pt in a card, 15 pt
in the payment card). The payment card carries the due date as a plain sentence, the GiroCode to
its right, and a single-line caption sized to the code's own width; the amount is printed once,
in the totals card, and not repeated in the payment card (product-owner decision). The note and
the tax note share one title-column width so their body text always starts at the same x,
whichever combination is present.

== Consequences
* Two binaries in the worker image (JVM app and Typst CLI) instead of one; both pinned, both
  checksum-verified, both reported by status endpoints. `TypstToolchainPinTest` keeps the
  runtime image, the test image and the reported version in lockstep.
* Typst is pre-1.0: a version bump is a task of its own, with `TypstCompileIT` rerun.
* No visual template designer, and none needed: one standard Typst template ships with the
  product, changed in code or by the operator. Customers do not author layouts.
* `Dockerfile.native` does not yet install the binary or fonts; a native worker needs the same
  stage before Typst is used there.

== Alternatives Considered
JasperReports 7 with `.jrxml` templates (rejected; it rendered the base PDF before Typst):

* `.jrxml` templates are compiled at runtime through `jasperreports-jdt` and may contain
  arbitrary Java expressions — an uploaded layout is executable code, which is why user-supplied
  templates needed a signature and reconciliation scheme.
* Geometry is expressed in pixel bands of a report designer, not in the millimetres DIN 5008
  is written in; the layout inspector had to measure what the engine actually produced.
* Output is not byte-deterministic (timestamps, object ordering), which weakens golden tests
  and the archive's content hashes.
* The runtime class generation is at odds with a native image (`Dockerfile.native`) and keeps a
  large, reflection-heavy dependency tree in the worker.
* Keeping it as a reserve fallback module behind a Maven profile and a `ServiceLoader` hook
  (briefly the case on 2026-09-27) added code that could only rot, since Typst needs no
  fallback engine in production.
